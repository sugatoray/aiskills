# WISDOM.md — Constraints, Traps, Ditches, and Wisdom

Hard-won lessons for this project. Read this LAST, right before editing code, so it's freshest in mind.

## Constraints — respect and conform to them
Things you must respect or conform to (external requirements, API contracts, platform limits).

- The install folder is `~/.config/sugatoray/aiskills/` (skills in `skills/`, the marketplace file in `.claude-plugin/`), as the user specified. Only `AISKILLS_HOME` overrides it. Keep it even though the npm scope is `sugatoray-ai`.
- Package name is `@sugatoray-ai/aiskills` (the user's npm org). Commands: `aiskills`, `ais` (same) and `aix` (= `aiskills --route`). Don't add or rename commands unasked: each is a public name users script against. `ask` is taken by Amazon's Alexa Skills Kit CLI.
- The package ships `skills/` **flat**; `.aiskills/layout.json` + `.aiskills/nested/` must keep every other repo file so `--nested` can rebuild the repo's `skills/` byte for byte. Skill folder names come from `SKILL.md` `name:`, which must be unique and folder-safe (`vendor()` refuses otherwise).
- `marketplace.json` is used **only** to define skill groups. Never install anything as a Claude Code plugin from it; all installs go through `npx skills add`.
- Group name = the plugin entry's `name`, exactly. The alias (name minus `-skills`) and the `all` group are CLI inventions; the README must keep saying so.
- npm never runs uninstall lifecycle scripts, so `aiskills uninstall` has to be run before `npm uninstall -g`.
- npm 7+ hides install-script output unless `--foreground-scripts`; pnpm and bun skip install scripts unless allowed; `--ignore-scripts` skips them too. That's why the package has none (AIS-7): `aiskills install` is the one way in, the same under every package manager.
- `bin/aiskills.mjs` is a thin entry point; the code is in `src/scripts/core/` (what ships: `cli.mjs`, `installer.mjs`), `src/scripts/pack/` (`vendor-skills.mjs`, `skillsignore.mjs`, run at `npm pack`) and `src/scripts/docs/` (docs/banner builders, `themes.mjs`, `templates/`); `src/scripts/README.md` explains them, and tests in `src/test/`; `package.json`, README and docs stay at the package root. `"bin"` points at `bin/aiskills.mjs`, which only imports `src/scripts/core/cli.mjs`.
- **Layout is the user's call; don't rearrange it unasked.** It was changed four times in one session before settling: `bin/aiskills.mjs` (thin entry point at the package root) → `src/scripts/cli.mjs`; all other code in `src/scripts/`; tests in `src/test/`; `package.json`, README and docs at the package root. Later the user split `src/scripts/` into `core/` (the package and its packaging) and `docs/` (docs, banner, `docs/templates/`); then moved the packaging scripts into a third group, `pack/`. Imports only point down (`docs/` → `pack/` → `core/`), which `packaging.test.mjs` checks.
- **Versions:** `0.1.0`, `0.2.0` and `0.3.0` were never published and are marked so in the CHANGELOG; `0.4.0` is the first published one (2026-11-09) and its section is now closed. `0.5.0` was dated 2026-11-09 at the bump, before publishing, at the user's request ("date it now"); its section is closed too. New work goes under `## [Unreleased]`. The user's call overrides the old "date only when published" rule. `0.6.0`, `0.7.0` and `0.8.0` were dated at their bumps too (2026-11-11), following that choice; the user can ask for `- Unreleased` instead. `0.9.0` and `1.0.0` were dated 2026-11-11 the same way; `1.0.0` reached npm at 2026-11-12T01:06Z, still 2026-11-11 in the maintainer's time zone (US Eastern), so its date was kept. A new or updated bundled skill means deciding on a package bump in the same PR (the user's rule: the package vendors the skills); `0.7.0` was bumped in #161, the PR that added `dynamic-promo-video`. Don't give an unpublished version a date. Between releases `package.json` may carry `x.y.z-dev` (from `1.3.0-dev`, 2026-11-13), with the CHANGELOG section `## [x.y.z] - Unreleased`. Never `x.y.z.dev`, which isn't SemVer; don't publish a `-dev` version, or if you must, use `--tag next`. While the package is at `-dev`, the docs examples show `installed: x.y.z-dev (not published on npm)`; at release, set `x.y.z` and regenerate. Fix version examples line by line: the pages use `…` lines for output that changes between runs, and pasting the test's "actual" output overwrites them.
- **Every user-visible change gets a line under `## [Unreleased]` in `CHANGELOG.md`**, in the same commit. Bump by the rules at the top of that file: MAJOR for anything that breaks existing use (removed/renamed commands or options, changed defaults, a different install folder or layout), MINOR for additions including new or updated bundled skills, PATCH for fixes only. Bundled skills keep their own changelogs.
- **Security protections that must stay** (all tested; see `SECURITY.md`): `npx` runs a pinned `skills@SKILLS_CLI_VERSION` (bump only after `npm run test:e2e` with the new version); registry text from `npx skills find` is untrusted and checked with `isSafeRegistrySpec`; on Windows `runSkills` refuses `cmd.exe` shell characters; anything that replaces or deletes files in the install folder calls `assertInstallFolder` first.
- **Generated docs are never edited by hand:** `docs/docsite/skills/*`, the landing page's list between `<!-- skills:start -->`/`<!-- skills:end -->`, `llms.txt`, `llms-full.txt` and `index.html`. Change the source (a page, a skill's `SKILL.md`) and run `npm run docs`; the tests fail while any of them is stale. New docs pages must be listed under a `### Section` of `docs/docsite/README.md`, or the HTML build refuses them.
- **Docs examples that show `aiskills` output need `<!-- verify -->`** (or `<!-- verify: list=… find=… -->`); the docs test runs them against the real skills and compares exactly. A version bump changes the `--version`/`--help` examples and the HTML.
- The `files` list in `package.json` decides what ships. The scrolls files, `CLAUDE.md` etc. must stay out of the tarball. Anything `"files"` lists can't be excluded by `.npmignore` (npm's documented rule), so `.npmignore` only matters for paths outside `"files"`; its root-anchored memory-file entries (`/CLAUDE.md`, …) are a safety net for if `"files"` is removed. Keep the leading `/`, or same-named files inside bundled skills would be dropped too.

- **The docs builder must keep reading the newest release's docs.** `build-site.mjs` builds the stable page from the newest `aiskills-vX.Y.Z` tag's `docs/` with the current `build-docs-html.mjs`. So a change to what the builder expects (the landing page's `### Section` lists, `images/`, the banner markers) must still accept that release's docs, or the website's stable page breaks until the next release. Check with `npm run docs:site` while `package.json` is `-dev`. The workflow test does this whenever the clone has the tags.

## Traps — avoid them always
Specific bugs that have bitten this project before — avoid repeating them.

- **npm drops nested `.gitignore`/`.npmignore` files** from the tarball and applies them as ignore rules while packing. The vendor step renames them to `_gitignore`/`_npmignore`; `syncSkills` renames them back. (Hit by `skills/newsletters/newsletter-ai/.gitignore`.)
- **The package's own `.gitignore` ignores `/skills/`.** Without a `.npmignore` present, npm would fall back to `.gitignore` and ship no skills. Keep `.npmignore`.
- **Nested `npx` under npm (`npx @sugatoray-ai/aiskills`, `npm exec`, formerly postinstall) can fail with "skills: not found"** because npm exports `npm_config_global`, `npm_config_prefix` and friends. `childEnv()` strips `npm_*` variables except the registry, proxy and cert ones.
- **`spawnSync` with a deleted `cwd` throws ENOENT.** After `--purge` the install folder is gone; `runSkills` falls back to `$HOME`.
- **An env default of `skills: ['*']` meant "everything"** and silently overrode `-G`. The default is now `[]`; "everything" is `null` from `selectedSkills`.
- **A blanket find-and-replace of paths also rewrites history.** Replacing `src/aiskills/` → `src/scripts/` across the scrolls changed a `HANDOFF.md` line about the earlier `src/aiskills/` → `src/packages/aiskills/` move. Replace paths file by file and re-read history lines.
- **`sed` with `|` as its delimiter can't use `\|` alternation**: `s|^/\(A\|B\)|...|` silently changes nothing. Use another delimiter or Python for regex edits, and check the edit actually happened before trusting a test result that depends on it.
- **A static `import` runs before the code above it.** `bin/aix.mjs` must set `AISKILLS_ROUTE` and then `await import(...)` the CLI; with `import "..."` the CLI would read its options before the variable exists.
- **Don't commit while a background check has a file deliberately broken.** A mutation check that edits a source file and restores it afterwards leaves the tree wrong until it ends; wait for it (e.g. the Stop hook asked for a commit mid-run) before `git add`.
- **`.skillsignore` follows `.gitignore` exactly, including two surprises:** a `/` in the middle of a pattern anchors it (`meta/x.md` does *not* match `g/meta/x.md`; use `**/meta/x.md`), and `#` is a comment only at the start of a line (`*.log  # logs` is one pattern that matches nothing useful). Both bit while writing the tests and the README example; check examples by running them through `parseIgnore`/`isIgnored`.
- **Moving files can leave tests that can never fail.** After an earlier move, the "doesn't ship" check still matched the old `src/aiskills/` paths, so nothing could ever trip it. When paths change, grep the tests for the old ones, and give each negative check a positive guard (here: the file list is non-empty, and a layout test names the real folders).
- **A plain name in `"files"` matches at any depth.** `"README.md"` also shipped `src/scripts/README.md`, because npm matches it in every folder that ships other files; `"/README.md"` matches only the root. `.npmignore` can't undo a `"files"` match. The packaging test that names what may not ship caught it.
- **A `display` rule beats the `hidden` attribute.** The gear menu's `display: grid` kept it always visible; any element toggled with `hidden` that also sets `display` needs `[hidden] { display: none; }`. The browser test caught it.
- **A marker comment must not contain its own end marker.** `/* banner:css:start (... up to banner:css:end) */` made a split-based test see an empty region (the line-anchored builder regex was fine). Keep marker comments free of the other marker's name, and drop stale references (it still named callai's Python builder).
- **Theme rules vs state classes:** `:root[data-skin=x] #banner` (1,2,0) beats `#banner.ink-dark` (1,1,0), so a theme's bright accents silently overrode dark ink on white. Scope theme accents as `#banner:not(.ink-dark)` and give each theme separate dark-ink accents.
- **A preview that lets you pick any combination will produce unreadable ones.** callai's banner page allowed light ink on white, and a transparent PNG always carried light ink, so on a white page the text measured 1.16:1. Measure contrast per combination (WCAG ratio, ≥ 4.5:1), disable the ones that fail, and export a transparent image in both inks with the ink in the file name.
- **Relative image paths in a README don't work on npmjs.com.** Use an absolute `raw.githubusercontent.com/<owner>/<repo>/master/...` URL (as callai does); it 404s until the file is on `master`.
- **Measure inside the border.** A scaled banner in a 1px-bordered box is `clientWidth` (2px narrower than its bounding box) wide; a test comparing with the outer width failed on correct code.
- **A check that silently skips what it can't parse proves nothing.** The first docs-example parser only matched unindented `<!-- verify -->` blocks, so examples inside numbered steps were skipped without a word; the first browser link check accepted a link to a missing page because the page had turned it into a valid GitHub URL. Make the check fail (or count) on what it skips, and mutation-test it.
- **Content can contain template syntax.** A skill description has `{{issue-number}}`, so "no `{{` anywhere in the built HTML" was a wrong test. Check only the template's own placeholders, and fill them before inserting content.
- **Backticks inside a JS template literal end it.** Generating Markdown code spans (`` `name` ``) inside `` `...` `` strings needs `\``; the generator broke with a syntax error the first time.
- **Hardcoded repo-root depth** broke when the package moved. `vendor-skills.mjs` walks up to the first folder with `skills/` and `.claude-plugin/marketplace.json`.
- **`export HOME=<tmp>` in a test shell** also breaks the next `git commit` (no identity). Set `HOME` per command, not with `export`.

- **Testing a prompt under `script` (pseudo-terminal): typing ahead echoes the answer before the prompt**, and the prompt line then shows no answer. `sandbox().tty()` runs a small driver that waits for `[y/N] ` on the output before writing the answer, as a person would.

- **pytest isn't installed in these sessions**, but the repo's Python skill tests (`skills/docs/create-lib-docs/tests`) need it: `pip install pytest` first, then `python3 -m pytest -q skills/docs/create-lib-docs/tests`.

- **Tests that derive "what ships" from `git ls-files skills`** must subtract what a `.skillsignore` leaves out (read `ignored` from `.aiskills/layout.json`); `shippable()` in packaging.test and `shippedSkillFiles()` in e2e do. They silently assumed no `.skillsignore` existed until `skills/newsletters/.skillsignore`.

- **Tests must never send a real skills.sh count.** The count runs a detached `npx skills add sugatoray/aiskills` after every successful install. The sandbox sets `AISKILLS_STATS=0` unless `sandbox({ stats: true })` (only `stats.test.mjs` and the docs examples, against the fake `npx`), and strips `DO_NOT_TRACK`/`DISABLE_TELEMETRY`/`CI` so results don't depend on the runner; `e2e.test.mjs` (real `npx skills`) sets `DO_NOT_TRACK=1`. A detached process writes to the fake-npx log *after* the CLI returns, so a test that checks `calls` of a stats-on sandbox must use `AISKILLS_STATS_FOREGROUND=1` or poll `b.calls()`.
- **`--stats` wins over `AISKILLS_STATS=0`** (flag > env > remembered > on), like `--nested` over `AISKILLS_LAYOUT`; only `DO_NOT_TRACK`/`DISABLE_TELEMETRY`/CI beat the flag. A test expecting `--stats` + `AISKILLS_STATS=0` to be off is wrong.
- **Don't call skills.sh's telemetry endpoint directly** (`https://www.skills.sh/tele/t`, found in `skills@1.7.6`'s `dist/cli.mjs`): it's undocumented and owned by the `skills` CLI. The count goes through the real CLI so it stays honest and follows the CLI's own rules (public repo check, opt-outs).

- **Interval open ends are plain ASCII: exactly one of `...`, `?` or `*`, never combined** (the user's choice; they wrote "…" meaning three dots, then added `?` and `*`). A Unicode `…` can turn into `?` in an old Windows console code page, which is partly why `?` is accepted too; `…` is still read as `...` but is never shown in help, docs or messages. Keep every suggestion copy-pasteable on Windows.
- **The variable is `AISKILLS_SKILLS_LIB_VERSION`** (renamed by the user so `_SKILLS_` isn't read as the bundled skills' version). `AISKILLS_SKILLS_VERSION` shipped in 0.4.0 and 0.5.0, so it was a deprecated fallback with a warning from 0.6.0 to 0.9.0. **1.0.0 removed it** (AIS-11, the user's decision; CHANGELOG **Removed**): it's no longer read at all (no warning; a bad value under it doesn't fail), and `reference/environment.md` may only document variables the code reads, so the old name is a sentence under `AISKILLS_SKILLS_LIB_VERSION`, not its own section. Old CHANGELOG sections keep the old name (history).
- **Range parts are separated by plain ASCII spaces only** (`' +'` in the regexes, never `\s`): `\s` let tabs, line breaks, U+2028 and non-breaking spaces through to `npx` and `cmd.exe` unchanged (found when the user asked whether the Unicode ellipsis could be abused). Intervals are safe either way: they're rebuilt from the version numbers.
- **An `AISKILLS_SKILLS_LIB_VERSION` override is announced once per command** (`skillsPackageSpec`, on stdout like the `running: npx` lines; the docs examples join stdout before stderr, so stderr would print out of order there), since the main abuse of the variable is a silent downgrade by whoever controls the environment.
- **npm's `min-release-age-exclude` doesn't apply to `npx`** (tested with npm 11.21.2 and 12.2.2; `npm install` honours it, even comma-separated). Only `--min-release-age=0`/`npm_config_min_release_age=0` or a range in `AISKILLS_SKILLS_LIB_VERSION` get `npx` past the rule. Don't tell users to exclude `skills`.
- **`runSkills` now reads `npx`'s stderr** (to spot npm's release-age error) and prints it when `npx` ends, so error lines arrive late instead of streaming. The `aiskills skills …` passthrough passes `interactive: true` to keep stderr on the terminal; keep that for anything that may prompt.
- **A pinned `skills` version younger than ~7 days breaks users with `min-release-age=7`** for every command that runs `npx` (hit with 1.7.6 on 0.5.0's release day). `npm run audit:skills` fails on that; run it before bumping `SKILLS_CLI_VERSION` and before publishing.
- **The `skills@<range>` argument is the one exception to the Windows shell-character refusal:** `cmdArgs` wraps it in double quotes (cmd.exe reads `< > | ^` as text inside them). That's only safe because `skillsVersionSpec` limits it to version characters (no `% ! " & ( )`). Never widen that grammar without rechecking cmd.exe quoting. Not yet run on real Windows.

- **Adding a bundled skill leaves hand-written lists stale while every test passes.** For `dynamic-promo-video` (#161) the tests forced the generated pages, banner counts and the `aiskills groups`/available-skills doc examples, but not the README's intro group list and group table, `docs/docsite/README.md` ("12 skills in 6 groups") or `concepts/skill-groups.md`'s table; they were caught only at the 0.7.0 bump. It happened again for `image-styles-skills` (#141): the skills PR was written against the repo only, so rebasing it onto `master` failed 17 package tests (`banner.test.mjs` hardcodes `13 skills · 7 groups` and the pill counts; doc examples snapshot `aiskills groups` and the `available:` lists), and the README/landing intro group lists ("…, video") were still missed until a grep. A PR that adds a skill anywhere under `skills/` is a package change: run the package's `npm test` on it. When a skill or group is added, grep the package for the old counts and for an existing group name (e.g. `personas-skills`) and update every hit.
- **Stage a new skill before running `npm test`.** `sandbox({ realSkills: true })` copies only git-tracked skills, so an untracked skill makes the counts, group lists and docs examples look stale (15, not 16) and sends you editing the wrong numbers. And never name a skill folder `build/`: the repo `.gitignore` drops it from `git add` silently.
- **Check the registry before calling a version unpublished.** The scrolls said 0.6.0 was "not merged or published" after it had shipped as `latest`; `npm view @sugatoray-ai/aiskills versions dist-tags --json` settles it in one call.

- **GitHub lists a PR's commits by committer date, not by history.** Adding a trailer with `git commit --amend` during a rebase (`-x`/`exec`) gives those commits a new committer date, while `--committer-date-is-author-date` leaves the others at their old dates, so the PR page interleaves them (seen on #141). When rewriting a PR's history, give every commit a committer date that rises in history order: `git rebase --force-rebase -x 'GIT_COMMITTER_DATE="@<n> +0000" git commit --amend --no-edit'` with `n` going up by one per commit. Check with `git log --format='%h %cd'` before force-pushing.

## Ditches — bad patterns or decisions to avoid
Bad patterns or decisions to never take, and why they were rejected.

- Don't reuse a merged PR's branch for new work. After a merge, put follow-up work on a **new** branch (the user asked for this explicitly). GitHub deletes the merged branch, so pushing to the old name recreates it.
- **`Closes #N` in a stacked PR does nothing until the PR targets the default branch.** GitHub only auto-closes issues on a merge into `master`; #193 (based on #184's branch) lists `Closes #194`–`#198`, which take effect only after #184 merges and #193 is retargeted. Merging a stacked PR into its base branch instead leaves its issues open; say so when filing them.
- **A stacked PR after its base is squash-merged:** if `git diff <old base commit> origin/master` is empty, either merge `master` in with `-s ours` (no force push; used for #147) or, when the user asks for a rebase, `git rebase --onto origin/master <old base commit> <branch>` and push with `--force-with-lease=<branch>:<old sha>` (used for #155). A force push needs the user's explicit request; one without it was denied earlier.
- Never add an install-time script (`preinstall`, `install`, `postinstall`, `prepare`). A package that rewrites agents' instructions during `npm install` is what scanners flag, and the script fails silently under pnpm, bun, `--ignore-scripts` and npm 7+'s hidden output. `packaging.test.mjs` enforces it (AIS-7).
- Don't add `s`, `l` or `u` as command aliases: `s` could mean `sync` or `skills`, `l` reads as `list` but sits next to `ls` (= `installed`), and many CLIs use `u` for "update". Prefer `npm`'s own short forms (`i`, `r`, `ls`).
- Don't make install-time behaviour opt-in through an env var. The install script stays (so scanners and pnpm still flag it), the hint it prints is hidden by npm 7+, and users lose the one-step install. AIS-7 removed the script entirely instead.
- Never run `npx skills` interactively from scripts; always pass `--yes` (scripts and CI have no TTY).
- Never install a skill a `--route` lookup found without the user's confirmation (`[y/N]`, default no, or `-y`); without a terminal, stop rather than assume yes. Pinned `owner/repo@skill` is the user's own choice and isn't asked.
- Never auto-pick among several registry matches for a name under `--route`. List them and make the user pin `owner/repo@skill`; it's third-party code with full agent permissions.
- A full `uninstall` (no `-s`/`-G`) must only remove skills whose recorded source is the install folder, even with `--route`.
- Don't copy a reference repo's layout without checking it actually has the shape asked for; `sugatoray/pptxdiff`'s `src/packages/*` have no inner `src/` (only its root package does). Say what you found and which part you're copying.
- Don't commit the vendored `skills/`, `.aiskills/` or `.claude-plugin/` copies in the package folder; `npm run clean` removes them. `LICENSE` is the exception: it is the package's own Apache-2.0 text, committed, and the vendor step must never overwrite it with the repo's MIT `LICENSE` (tested by SHA-256).

## Wisdom — best practices and Red/Green TDD
Best practices worth reusing.

- Always use Red/Green TDD while developing or fixing code.
- **Answer "what does `npx skills` do?" from its source, not memory.** `npm pack skills@<pinned>` into the scratchpad and grep `dist/cli.mjs`: that is how `--yes` without `--agent` was found to mean "detected agents + universal, or *all* agents if none detected", that `add` has no `--project` flag (so it asks for the scope when `--yes` is dropped), and where `lastSelectedAgents` lives.
- **`npx skills` copies a skill into its own folder** (`~/.agents/skills/<name>`, agents symlink to that), so refreshing `~/.config/sugatoray/aiskills/skills` changes nothing your agents see: re-run `npx skills add`. Its own `update` command skips local sources, so aiskills must do that itself (`aiskills upgrade`).
- **`npx skills list --json` gives agent display names, `--agent` takes ids, and the lock file stores no agents.** Map names to ids (exact dashed → punctuation-free → longest id the name starts/ends with: 79/79 of skills 1.7.6's agents) and report anything unmatched; never guess.
- **A self-upgrade must run the new code from the package manager's path, not its own** (`entry` = `<global root>/@sugatoray-ai/aiskills/bin/aiskills.mjs`): pnpm's real folder has the old version in its name and may be gone after the upgrade.
- **npm's download API: per-version counts exist for `last-week` only** (`/versions/<pkg>/last-week`; every other period is 404), package totals for any period but at most 18 months per request, and data ends yesterday (the `range` endpoint pads today with 0, so take the end from `/downloads/point/last-day`). Don't promise per-version history.
- **A docs page must work as `index.html` alone.** Phone apps and previews often get only that one file, so anything next to it (an `<iframe src>`, a link to a sibling `.html`) shows empty or 404 there, even though every desktop and HTTP test passes. Embed it (as the SVGs are, and now `DATA.staticHtml`, base64 so its `<script>` tags can't break the page's own), render it with `srcdoc`, open it in an in-page overlay, and test by copying `index.html` alone into an empty folder at phone size. Never leave a `src` for the browser to try first.
- **Design for a firewall + npm mirror.** Users behind Artifactory/Nexus/Verdaccio reach the registry but not github.com or api.npmjs.org, and some mirrors strip `time` from package metadata: never infer "not published" from `time`; list `versions`; name the registry in errors; prefer files that ship in the package over links (the user asked about this for the `rel` changelog line).
- **Node's `fetch` ignores `HTTPS_PROXY`** (ENOTFOUND behind this sandbox's proxy); run it in a child `node` with `NODE_USE_ENV_PROXY=1`. That also keeps a synchronous CLI synchronous.
- **A test server can't live in the test process when the CLI runs under `spawnSync`**: the event loop is blocked, so requests hang. Run the fake (here api.npmjs.org) as its own process (`sandbox().startApi()`), and kill it in cleanup; a stray one hangs a shell command (it bit a smoke test).
- **A new CLI option or message needs three doc touches or `npm test` fails:** a heading in `reference/cli.md` (every `a === "-x"` flag), every `new Error`/`warn` text in `reference/errors.md`, and the README summary line (`packaging.test.mjs` flag map). Then regenerate `llms-full.txt` (`build_llms_txt.py`) and `npm run docs:html`.
- **Run `npm test` before every change and after it.** New behaviour gets a test in `src/test/cli.test.mjs` (stand-in `npx` on `PATH`; assert the exact `npx skills` args via `skillsArgs`) or `src/test/unit.test.mjs`. Add a failing test first (Red/Green).
- Tests must never touch the real `HOME` or write vendored files into the package folder: use `sandbox()` / `repoCopy()` from `src/test/helpers.mjs`.
- **End-to-end recipe** (now automated as `npm run test:e2e`): `npm pack --pack-destination <tmp>` → `HOME=<tmp>/home npm install -g --prefix <tmp>/prefix <tgz>` → drive `<tmp>/prefix/bin/aiskills` with `HOME=<tmp>/home` → `npm run clean`.
- **Check the tarball:** compare `npm pack --dry-run --json` (with `_gitignore` mapped back) against `git ls-files skills`; they should be identical.
- **Fingerprint generated binaries.** A PNG can't be compared pixel by pixel across machines, but it can carry `tEXt` chunks (here the theme and the SHA-256 of its source page); a test then catches a stale image exactly. CRC-32 is a few lines; no dependency needed.
- **One data module for shared choices.** Both gear menus, the page CSS and the banner CSS come from `themes.mjs`, and contrast is tested from the values (offline, every theme × mode) as well as on the rendered banner. List the default first so menus open on it, and load only the default's fonts up front.
- **Maintainer docs drift when updated piecemeal.** Each change patched `docs/meta/` paths, yet a full read after the folder split still found a module table missing four modules, a release flow that no longer matched practice and stale requirements. After structural work, reread ARCHITECTURE, FEATURES and MAINTAINERS end to end, and check their links and named functions mechanically.
- **Tests keep docs correct; a read-through keeps them findable.** On `/create-lib-docs --update`, the docs tests showed the reference and examples still matched the code, but only reading the landing page as a newcomer showed that nothing told readers about `index.html` or its themes. Do both on every refresh.
- **Mock up first, then generate.** The banner was shown as a mockup, then made editable, and only built into the repo once approved; its values (counts, group names and order, demo output) are then generated from the package, so the committed banner can't drift from what ships. Expect generated order (`marketplace.json`) to differ from a hand-made mockup, and say so.
- **Write docs from what runs, not from memory.** Running every docs example found a missing output line and a real bug (`uninstall -n` showed an unpinned `npx` command); checking against the live `skills --help` removed a `check` command that doesn't exist. Generate per-skill docs from the vendored package (what ships), not the source tree.
- `npx skills list --json` gives `source` and `sourceType` per skill (`skills@1.7.6` rows also have `path`, `sourceUrl`, `status`, `scope`; `agents` holds display names like `Claude Code`). Bundled rows are `sourceType: "local"` with `source` equal to the install folder.
- `npx skills add <empty dir> --list --agent <bogus>` prints "Valid agents: ..." and installs nothing; that's how agent patterns get their list.
- `SKILLS_API_URL=http://127.0.0.1:<port>` points `npx skills find` at a local fake (`GET /api/search?q=` → `{"skills":[{name,id,source,installs}]}`), so `--route` can be tested offline.
- Do every lookup and validation before the first install, so a bad entry changes nothing.
- **Write the threat model, then check the code against it.** Listing what the package writes, which network calls happen and what reaches a shell found three real bugs (unchecked registry text into `cmd.exe`, an unguarded recursive delete of `AISKILLS_HOME`, an unpinned `npx` package) that 100+ tests had not, because no test asked those questions.
- **Prove a new test can fail.** Temporarily break the thing it guards (remove the line, change the condition), see the test go red, then restore. The first `.npmignore` test passed even with the entries broken, because `"files"` was doing the work; only the deliberate break showed it.
- npm only needs `"bin"` to point at a file with a `#!/usr/bin/env node` first line; the `bin/` folder is just a convention. A thin `bin/` wrapper keeps the real CLI module free of the shebang and makes the command's entry point easy to find.
- Group membership is computed from each skill's *original* folder in `layout.json`, never from where the skill sits now, so it's independent of the flat/nested choice. Without `layout.json` (an old package or the test fixtures used as an install root), it falls back to scanning `skills/` under each group's `source`.
- **Shipping skills in npm packages** (checked in `skills` CLI 1.7.6): `npx skills experimental_sync` reads skills from a project's `node_modules` packages at `<pkg>/SKILL.md`, `<pkg>/skills/<name>/SKILL.md` or `<pkg>/dist/skills/<name>/SKILL.md`, one level only, and a project can list packages under `"skills": ["npm:<pkg>"]` in its own `package.json`. Usual practice: skills are data in a flat `skills/` folder, code in `src/`, a strict `files` list, and no side effects at install time (pnpm and bun skip install scripts unless allowed, `--ignore-scripts` skips them, and security scanners flag them).
- **The repo root's `.agents/skills/` and `.claude/skills/` symlinks (#230) don't reach the package.** Vendoring reads `skills/` through `.claude-plugin/marketplace.json`. With the links in place, the packed file list was unchanged, and `npx skills@1.7.6 add . --list` found each skill once. If more skills are linked, or the link layout changes, recheck both.
